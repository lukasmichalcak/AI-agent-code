# Three SDKs for cross-chain transfers: verified capability extract

**Version and observation date:** LI.FI `@lifi/sdk` 4.10.0; ParaSpell `@paraspell/sdk` 14.4.0; Wormhole `@wormhole-foundation/sdk` and `sdk-connect` 6.1.5; checked 4 October 2026. Function names and types were checked against the published packages. Network observations below provide a timestamped snapshot.

| SDK | Send: entry point | Assets and destinations | Fee information | Balance |
| --- | --- | --- | --- | --- |
| **LI.FI** | `getQuote` for one option or `getRoutes` for several; `executeRoute` signs/submits through a configured wallet provider | `getChains`, `getTokens`, `getConnections`; obtain a quote for the chosen chain, token and amount | Quote/route step `estimate.feeCosts[]`, `gasCosts[]`, `toAmount`, `toAmountMin`, duration | `getTokenBalance`, `getTokenBalances`, `getTokenBalancesByChain` for specified tokens and a matching provider |
| **ParaSpell** | `Builder().from().to().currency().recipient().sender().build()`; sign and submit the built transaction or call builder `signAndSubmit()` | `getSupportedDestinations(origin,currency)`, `getSupportedAssets(origin,destination)`, asset metadata and fee-asset registry | Builder `getXcmFee()`, `getTransferInfo()`, `dryRun()`; origin, hops and destination have distinct fee assets and amounts | `getBalance({address,chain,currency?,api?})` returns `Promise<bigint>` |
| **Wormhole** | Route resolver: `supportedDestinationTokens` → `findRoutes` → `validate` → `quote` → `initiate`; direct Token Bridge: `wh.tokenTransfer(...)` | Source asset must be supplied or obtained from a separate registry; `resolver.supportedDestinationTokens(sourceToken,sourceChain,destChain)` tests destinations for registered routes | Successful `route.quote()` reports source/destination tokens, optional `relayFee`, optional `destinationNativeGas`; source-network gas needs a separate estimate | `wh.getBalance(chain,tokenAddress,walletAddress)` returns `Promise<bigint \| null>` |

## LI.FI

- **Send.** `getQuote(client,{fromChain,toChain,fromToken,toToken,fromAddress,fromAmount})` returns one `LiFiStep` with an estimate and unsigned `transactionRequest`. `getRoutes(client,{fromChainId,toChainId,fromTokenAddress,toTokenAddress,fromAmount,...})` can return several multistep routes. `executeRoute(client,route,options?)` handles the configured provider's approvals, signatures, submission and progress. Amounts use integer strings in the token's smallest units. A connected wallet still has to approve signatures. [SDK route guide](https://docs.li.fi/sdk/request-routes) · [Execution guide](https://docs.li.fi/sdk/execute-routes)
- **Assets and destinations.** `getChains` and `getTokens` list candidates; `getConnections` checks connected asset pairs using `fromChain`, `toChain`, optional tokens, and bridge/exchange allow, deny or prefer filters. A listed token or chain does not itself give a usable quote at a particular amount. Use chain ID and token contract address to identify the asset. A **type/implementation mismatch** matters in 4.10.0: `ConnectionsRequest` permits `allowSwitchChain`, `allowDestinationCall`, `chainTypes` and protocol filters, but `getConnections` serializes only chain/token selectors and the six bridge/exchange filters. Passing the other fields does not apply those filters in this version; enforce route constraints at quote/route selection. [Chain/tool guide](https://docs.li.fi/sdk/chains-tools)
- **Fees.** Read `step.estimate.feeCosts[]` with each fee's token, amount, USD estimate and `included` flag; read `gasCosts[]` separately for source transactions. `toAmountMin` is the slippage-protected minimum. A fee marked `included` is already reflected in the quoted output; do not add it to the source–destination difference again. Quotes and gas estimates can change before signing. [Quote API schema](https://docs.li.fi/api-reference/get-a-quote-for-a-token-transfer)
- **Balances.** In 4.10.0, `getTokenBalance(s)` and `getTokenBalancesByChain` require requested token objects and an appropriate wallet provider. `getWalletBalances` was **removed in v4.3.0**; the older token-management page has not caught up. The implementation of `getTokenBalancesByChain` may return the supplied token objects without balance amounts for a mismatched provider/chain type, so check the returned amount field before treating a token as funded. [SDK changelog](https://docs.li.fi/changelog/monthly-updates) · [Published package](https://www.npmjs.com/package/@lifi/sdk)

**Testnet evidence.** LI.FI's March and August 2026 changelog entries add Sepolia networks, while its older integration-testing page still recommends mainnet tests. The 4.10.0 SDK returned five Sepolia/Arc testnet chains in `getChains` on 4 October 2026. The queried Arc Testnet → OP Sepolia pair returned zero connections. Treat testnet availability as a route-specific observation: inspect connections, then request a quote for the precise token and amount before selecting a test. [Changelog](https://docs.li.fi/changelog/monthly-updates) · [Testing guide](https://docs.li.fi/sdk/testing-integration)

## ParaSpell

- **Send.** The v14 builder takes origin, destination, a currency selector with base-unit amount, recipient and sender. `build()` returns an unsigned transaction; signing/submission uses a compatible wallet or builder `signAndSubmit()`. An Ethereum-origin Snowbridge path also needs its relevant EVM extension and wallet. [Sending XCM](https://paraspell.github.io/docs/xcm-sdk/send-xcm.html) · [v14 migration](https://paraspell.github.io/docs/migration/v13-to-v14.html)
- **Assets and destinations.** `getSupportedAssets(origin,destination): TAssetInfo[]` and `getSupportedDestinations(origin,currency): TChain[]` query bundled route/asset metadata. `getFeeAssets(chain)` lists locally registered fee assets. Resolve ambiguous symbols by chain and asset ID/location. The registry gives candidates; live fee and dry-run checks evaluate the proposed transfer. [Asset package](https://paraspell.github.io/docs/xcm-sdk/asset-package.html)
- **Fees.** `getXcmFee()` returns `{success,origin,destination,hops}` with fees in each chain's fee asset and a `feeType` describing estimation method. `getTransferInfo()` includes `chain`, `origin`, `hops`, `destination` with balances, estimated receipt and fee information. In **v14.4.0**, it has no top-level `assetHub` or `bridgeHub` fields; intermediate chains belong in `hops`. `dryRun()` simulates origin and destination behavior. `getParaEthTransferFees(ahApi?)` is a separate Snowbridge helper returning `[bigint,bigint]`. [XCM utilities](https://paraspell.github.io/docs/xcm-sdk/xcm-utils.html)
- **Balances.** The public PAPI package signature is `getBalance({address,chain,currency?,api?}): Promise<bigint>`. Omit `currency` for the native asset. The optional parameter is `api`, not `client`. Use the asset registry to choose tokens when more than one balance is needed. For an Ethereum-origin Snowbridge token, the separate `@paraspell/evm-snowbridge` package declares `getTokenBalance(walletClient,symbol): Promise<{balance: bigint; gatewayAllowance: bigint}>`.

**Read-only Paseo run.** With the public development account Alice (`5GrwvaEF5zXb26Fz9rcQpDWS57CtERHpNehXCPcNoHGKutQY`), ParaSpell 14.4.0 found PAS on **AssetHubPaseo → PeoplePaseo** and returned a source balance of `75459876616612` base units. For a simulated send of `10000000000` base units (1 PAS), `getXcmFee()` returned success, `315345638` base units origin fee and `3168127` destination fee, both with `feeType: dryRun`; `dryRun()` reported success on both chains; `getTransferInfo()` estimated `9996831873` base units received. These figures are one 7 October snapshot for a **public account**, not a submitted transfer or evidence of control of its funds.

## Wormhole

- **Send.** The resolver checks destination tokens for a supplied `TokenId`, finds route classes applicable to a specific request, then each route validates, quotes and initiates. The direct `wh.tokenTransfer` path supports the Token Bridge protocols exposed by the pinned package. Manual completion needs a destination action and gas. The exact route classes registered determine coverage. [SDK guide](https://wormhole.com/docs/tools/typescript-sdk/get-started/) · [Route example](https://github.com/wormhole-foundation/wormhole-sdk-ts/blob/main/examples/src/router.ts)
- **Assets and destinations.** Version 6.1.5's `RouteResolver` has `supportedDestinationTokens(sourceToken,fromChain,toChain)` and `findRoutes(request)`. It has **no** `supportedSourceTokens` or `sortRoutes`. Obtain candidate source tokens from a chosen token list, wallet holdings or protocol metadata, then ask the resolver for matching destinations and routes. Compare quoted routes in application code. Token Bridge may deliver a wrapped asset; CCTP supports native USDC only where configured. Record the exact destination token address. [Published package](https://www.npmjs.com/package/@wormhole-foundation/sdk-connect) · [Route concepts](https://wormhole.com/docs/products/connect/concepts/routes/)
- **Fees.** `route.quote()` can contain `sourceToken`, `destinationToken`, optional `relayFee`, optional `destinationNativeGas`, warnings and expiry. There is no general numeric fee total across unlike assets and no source-chain network gas in this generic quote type. For the selected route, obtain source gas from its transaction and the chain RPC or wallet; for manual completion also budget destination gas. [Published `sdk-connect` package](https://www.npmjs.com/package/@wormhole-foundation/sdk-connect)
- **Balances.** The current `sdk-connect` declaration and runtime expose `wh.getBalance(chain,tokenAddress,walletAddress): Promise<bigint|null>`, where `tokenAddress` can be `'native'` for a native asset. Query each selected token separately. A live 6.1.5 call for the public `0x000000000000000000000000000000000000dEaD` address returned a `bigint` native balance on Sepolia; this confirms the method works for that test case. The precise meaning of `null` can depend on platform implementation.

## Already tested vs untested yet 

The local runs used the exact package versions above. LI.FI returned a quote for **1 USDC, Arbitrum → Base** with expected output `0.993818 USDC` at 06:54 UTC, three `included` fee entries, estimated source gas in ETH, and an unsigned transaction request. An earlier quote returned `0.993813 USDC`, demonstrating the need for multiple timestamped tests. ParaSpell returned the Paseo balance, fee estimate, dry run and transfer info above. Wormhole initialized on Testnet and answered a Sepolia native-balance query. The two unsupported Wormhole resolver methods were also absent at runtime. **No transaction was signed or broadcast.** The files [`sdk-readonly-check.mjs`](./sdk-readonly-check.mjs) and [`read-only-run-2026-10-04.json`](./read-only-run-2026-10-04.json) accompany this extract.

Run the script in a fresh Node.js 20.19+ directory after installing `@lifi/sdk@4.10.0`, `@paraspell/sdk@14.4.0`, `@paraspell/descriptors@14.4.0`, `polkadot-api@3`, `@wormhole-foundation/sdk@6.1.5` and `@wormhole-foundation/sdk-connect@6.1.5`. Copy the `.mjs` file into that directory and run `node` [`sdk-readonly-check.mjs`](./sdk-readonly-check.mjs)` > result.json`. On a network that requires an HTTPS proxy, set `NODE_USE_ENV_PROXY=1`. Public quotes and balances may differ on a later run.

To establish **actual transfer outcome and paid fees**, use a wallet you control with a small amount of Paseo PAS and the required fee asset. Re-run the ParaSpell balance/fee/dry-run checks using that wallet, sign one AssetHubPaseo → PeoplePaseo transfer, save the source extrinsic hash and finalized result, inspect the destination transfer and balance change, and compare observed fees and received amount with the preceding estimate. For LI.FI, choose a pair that actually returns a quote; its listed testnets do not guarantee an executable pair. The same principle applies to Wormhole's chosen route. Record the network, token identities, amount, SDK version, quote time, estimated and observed costs, signature count, destination receipt and final status. A testnet run establishes that route at that time; repeated trials and adverse cases are needed for reliability claims.

**Implication for the thesis.** All three SDKs already perform substantial route discovery, quoting and execution. The candidate agent contribution is translating user intent into correctly identified assets and hard constraints, comparing eligible results across these distinct systems, obtaining explicit approval, and detecting incomplete or incorrect outcomes. A rule-based orchestrator using the same SDK access is the comparison baseline. Evaluate task completion on the intended destination asset and amount, constraint violations, estimation error, elapsed time, intervention and failure recovery across repeated tasks. This follows the behavior/capability/reliability/safety distinction in Mohammadi et al., *Evaluation and Benchmarking of LLM Agents: A Survey* (2025), supplied with the thesis sources.

For an agent that uses LI.FI, its own [integration guide](https://docs.li.fi/agents/overview) recommends REST for a general backend agent, the SDK for a signing frontend, and MCP for compatible hosts. Its [MCP server](https://docs.li.fi/mcp-server/overview) returns unsigned transactions and does not broadcast them.
